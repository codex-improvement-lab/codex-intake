# Product insights

## 1. “Prompt quality” often starts as input debt

The user is not blocked on wording. They are blocked on assembling evidence spread across modalities and deciding what is safe to share. A better prompt template cannot identify which screenshot a claim came from or whether a pasted log contains a credential.

**Product implication:** optimize the minute before the conversation, not another prompt-writing canvas inside it.

## 2. Provenance is an editing affordance

Source pointers are usually framed as audit metadata. Here they answer an everyday question: “Why did the brief say this?” A click takes the user back to the evidence, so they can correct an over-broad rule before Codex inherits it.

**Product implication:** put the pointer beside each editable sentence, not in a hidden provenance appendix.

## 3. A deterministic first pass is a feature

A model could write smoother summaries, but requiring a key or sending raw material away recreates the privacy problem at the first step. Bounded rules are fast, challengeable, testable, and honest about uncertainty.

**Product implication:** local rules produce candidates; the human supplies meaning. Model enrichment can be an explicit later mode, never the prerequisite.

## 4. Privacy review belongs before “copy”

Warnings after a prompt is submitted are too late. Codex Intake makes the risk count part of the brief toolbar and strips raw bodies from the portable export by construction.

**Product implication:** the handoff button should communicate what will not be copied, not only what will.

## 5. Done-when must remain falsifiable

“Fix the bug” is not a task contract. The first useful criteria come from observed errors, recorded commands, explicit expectations, and privacy requirements. When the input lacks a reproduction or expected outcome, the product raises a gap instead of fabricating a criterion.

**Product implication:** acceptance criteria and missing evidence are two sides of the same intake model.

## 6. The strongest integration is not always the deepest

MCP Apps and App Server can produce richer native-adjacent experiences, but they add hosting/client constraints unrelated to this proof. A local Web UI is immediately demonstrable; a skill and CLI keep it composable.

**Product implication:** choose integration depth based on the irreducible workflow boundary, not novelty.

## Falsifiable next questions

- Does a source-linked brief reduce clarification turns compared with pasting the same pile directly?
- Do users act on privacy warnings, or do they habituate to them?
- Is local OCR correction faster than manual transcription for real screenshots?
- Which generated done-when rules survive user editing?

These require observed users and real inputs. Automated fixtures do not answer them.
